## Testing strategy

> Sebastian and Claude (Chat) settled on a hybrid approach (Option D) on 2026-05-02. The full discussion is in chat history; the operational shape lives here so future cycles inherit it without re-deciding.

**Decision:** Stocknify ships features faster than it tests them today. Rather than retroactively building coverage or stalling Phase 4 for a test-first rebuild, the project introduces test infrastructure incrementally, anchored to actual feature cycles.

**Rules going forward:**
- A dedicated `TEST_HARNESS_FOUNDATION` cycle (Cycle TH in NEXT.md) lands the Backend Fastify test harness before the next feature cycle (Cycle B). Without that cycle, no backend tests exist and there is nothing to add tests *to*.
- After Cycle TH, every cycle that touches Backend code ships at least one test for the touched endpoint or service surface. Frontend cycles stay test-free for now.
- Test failures are warnings, not red CI, for the first 5 cycles after Cycle TH. After that, flip to blocking. The grace window protects against harness-bedding-in friction.
- No coverage thresholds. No TDD enforcement. No retrofit-tests-for-existing-code initiatives. Adding tests for an old feature is a deliberate cycle, not a side-effect.
- E2E (Playwright) is explicitly out of scope until the onboarding flow has been stable for ≥30 days.
- Frontend test infra (React Testing Library) is out of scope until backend test discipline has held for ≥3 cycles post-TH. Tracked in NEXT.md backlog.

- **CI test-blocking flip** — Test step is currently `continue-on-error: true`. Flip to blocking after 5 cycles where the harness has been used. Tracked in NEXT.md backlog. *(Codex 2026-05-02 flagged this `[high]`; deferred per DECISIONS 2026-04-16 — soft-fail window is the explicit operational choice for the harness's bedding-in period, documented in DECISIONS 2026-05-02 (test-DB strategy) and NEXT.md.)*

## Backend

- **Deprecated `DELETE /v1/integrations/marketplace/:key/uninstall` (Cycle 4-A fallout).** The bulk-uninstall endpoint stayed in the API for backwards compatibility but has no caller in the web app anymore (`useUninstallIntegration` now hits `DELETE /v1/integrations/:id` per installation). It also has the dangerous footgun that under multi-install it tears down ALL installs of a key in one call. Right destination: delete the endpoint outright (no downstream consumers — single-operator MVP, only the web app calls the API). Hold a cycle or two for any external scripts to surface, then remove.
- **Marketplace install endpoint can still create SFTP rows (Cycle 4-A interim).** SFTP lives in `INTERNAL_INTEGRATIONS` so `POST /v1/integrations/marketplace/sftp/install` resolves and the setup wizard's existing call site works. Defer until F4/F5 from NEXT.md (Integration-hinzufügen UX cycle) touches the wizard.
- **Schedule-create handler validates credentials non-atomically (Cycle 3-D fallout, downgraded from Cycle 3-D scope item).** The schedule routes ship in Cycle 3-D and validate the referenced credential exists + tenant-bound + active before INSERT, but the read+write are NOT inside a SERIALIZABLE transaction. The symmetric race (admin schedules a job *while* another admin deletes the credential) is therefore open: a concurrent hard-delete after the validation read but before the schedule INSERT would surface a Prisma `P2003`/Postgres `23503` foreign-key violation as a 500. The credential-vault DELETE side already runs under SERIALIZABLE (Cycle 3-B Codex review fix), so the deletion blocks while a SERIALIZABLE schedule-INSERT holds a read on the credential row — but only if both sides are in matching SERIALIZABLE transactions. Promotion to a SERIALIZABLE schedule-create transaction with FK-violation rephrasing to `404 CREDENTIAL_NOT_FOUND` is a future hardening cycle. Add a regression test pinning the flow (concurrent DELETE → schedule-create returns 404, not 500). At MVP scale this race is exceedingly unlikely; the operator UI flow does not allow a sub-second delete-while-create against the same credential.
- **BullMQ scheduler orphaning on Redis reset (Cycle 3-D fallout).** Each schedule registers a BullMQ job scheduler under the schedule UUID. If Redis is wiped (TTL eviction, manual flush, container reset), the in-DB schedule rows survive but have no scheduler entry — they appear active in the UI but never fire. Symmetric: a developer running `redis-cli flushall` against the dev queue Postgres has no easy "re-register all" path today. Right fix: a startup reconciler that walks `IntegrationSchedule` where `isActive=true && deletedAt IS NULL` and `upsertJobScheduler`s each one. Idempotent by design (the upsert side does the right thing). Hold off until a real incident motivates it; for MVP a manual toggle-off/on cycles the scheduler.

Still deferred: success-path coverage (load → stream → success → schedule.lastRun* + integration health → `'healthy'`); partial-path coverage (some rows error → `status='partial'` + `'degraded'` health); consecutive-failures escalation 1→2→3 → healthStatus from `'degraded'` to `'failing'` (would need three full final-attempt invocations across separate cron ticks).
